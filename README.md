# TravelNext

**"Where should I travel next?"** — an explainable travel recommendation engine
built entirely on free, openly licensed data.

No paid APIs. No API keys. No cloud account. No credit card. It runs on a
laptop with 8GB of RAM, and once the dataset is ingested it runs fully offline.

---

## Problem

People usually know where they have *been*. They are much worse at working out
where to go *next*. Search engines answer "top 10 things to do in Rome" but not
"given that I loved Amsterdam, Berlin and Prague, and I have five days in
September on a mid-range budget, where should I go?"

The naive answer — recommend whatever is most popular — sends everybody to
Paris, London and Rome. A useful system has to learn what a particular
traveller responds to, and then explain itself well enough to be trusted.

## Solution

A two-stage recommender that learns from travel history and **measured**
destination characteristics, and justifies every suggestion with the numbers
behind it:

```
User travel history + trip context
              │
              ▼
   ┌──────────────────────┐
   │ Stage 1: Candidates  │  content · collaborative · geographic · popularity
   │   ~150 destinations  │  (four retrievers, unioned and de-duplicated)
   └──────────┬───────────┘
              ▼
   ┌──────────────────────┐
   │ Feature engineering  │  27 features: similarity, distance, season fit,
   │                      │  budget fit, popularity, candidate provenance
   └──────────┬───────────┘
              ▼
   ┌──────────────────────┐
   │ Stage 2: LambdaRank  │  LightGBM, optimising NDCG
   └──────────┬───────────┘
              ▼
      Top-K + explanations
```

A sample explanation, with every claim traceable to a computed value:

```
🇩🇰 Copenhagen — match 91%

✓ Similar in character to Amsterdam, which you visited   (cosine 0.47)
✓ Strong on museums and pedestrian streets               (percentiles 0.93 / 0.88)
✓ Travellers who went to Berlin often visit here too     (co-visitation 0.11)
✓ Good conditions in September (average 16°C)            (Open-Meteo normals)
✓ Only 622 km from Amsterdam, which suits a 5-day trip   (great-circle)
✓ You have not been here yet
```

## Data: free sources only

| Layer | Source | Licence | Key needed |
|---|---|---|---|
| Cities, coordinates, population | [GeoNames `cities15000`](https://download.geonames.org/export/dump/) | CC BY 4.0 | No |
| Article matching, descriptions | [Wikipedia REST + Action API](https://en.wikipedia.org/w/api.php) | CC BY-SA 4.0 | No |
| Popularity proxy | [Wikimedia Pageviews API](https://wikimedia.org/api/rest_v1/) | CC0 | No |
| Destination attributes | [OpenStreetMap via Overpass](https://overpass-api.de/) | ODbL 1.0 | No |
| Climate normals | [Open-Meteo archive](https://open-meteo.com/) | CC BY 4.0 | No |
| Cost proxy | [World Bank Indicators](https://data.worldbank.org/) | CC BY 4.0 | No |
| Continent / region | UN M49 classification (bundled in `src/data/regions.py`) | Public domain | No |

**Total cost to build and run: €0.** Nothing here has a paid tier that can be
triggered accidentally, and no request is made at recommendation time — the
served dataset is local parquet.

### How destination attributes are measured

The brief for this project forbids inventing feature values, and "how
cultural is this city?" is exactly the kind of number that is easy to fake.
Instead, every attribute is counted from OpenStreetMap within 4 km of the city
centre — actual mapped museums, bars, parks, beaches, monuments and pedestrian
streets — and turned into two complementary representations:

- **`profile_*`** — the category's *share* of that city's tourism POIs. Answers
  "what kind of place is this?" and is computed **within a single city**, so it
  is largely immune to OSM mapping density. The content model uses these.
- **`score_*`** — the global percentile of `log1p(count)`. Answers "how much of
  this does it have?" and is what the UI shows. This one *is* affected by
  coverage bias, so it is reported as a percentile and the bias is documented
  below rather than hidden.

A city with no OSM data keeps `poi_available = False` and `NaN` attributes. It
is never silently recorded as "a city with zero museums".

### Synthetic interaction data — stated plainly

**No real traveller data is used anywhere in this project.** No public dataset
of per-user travel histories exists under a licence permitting redistribution
at this geographic scope, so the interactions are generated by
[`src/data/synthetic_interactions.py`](src/data/synthetic_interactions.py) and
written to separate files from the real destination data.

Each generated user draws a preference archetype over the *measured* OSM
attributes, a home region, a budget and a seasonal preference. Trips then come
from one of three mechanisms — preference, popularity and geographic chaining —
so that no single model family can trivially explain all of the data.

**What this means for the metrics:** they measure how well each model recovers
the structure the generator injected. That is a real, non-trivial learning
problem and it validates the pipeline end to end. It is **not** evidence about
real-world recommendation accuracy, and no claim in this repository says
otherwise.

## Results

See **[reports/RESULTS.md](reports/RESULTS.md)** — generated by
`python -m src.analysis.report_results` directly from `reports/results.json`,
which is written by the experiment runner. No metric in the documentation is
typed by hand, so the numbers cannot drift away from the code that produced
them.

The comparison covers the popularity baseline, content-based, item-item
collaborative filtering, SVD matrix factorisation, the tuned hybrid, the
next-destination model and the LightGBM ranker, at K = 5, 10 and 20, with
Precision, Recall, F1, MAP, MRR and NDCG — plus popularity bias, catalog
coverage and diversity for every model.

Reproduce everything:

```bash
python -m src.evaluation.run_experiments
python -m src.analysis.report_results
```

### Evaluation protocol

- **Leave-last-n-out per user**, over each traveller's ordered trip sequence.
  A random split would let a model see later trips while predicting earlier
  ones — the classic temporal leak in recommender evaluation.
- **Models are fitted on the training split only.** `assert_no_leakage()` runs
  in the experiment script and fails loudly if any `(user, destination)` pair
  appears in two partitions.
- **The popularity baseline counts training interactions**, not the Wikipedia
  pageview proxy. Using the external proxy would make the "baseline" a content
  model in disguise and would not answer the question it exists to answer.
- **Trip context is treated as known at request time.** Month, duration and
  budget from the held-out trip are passed to every model, because in the
  product the traveller states them before asking. The destination — the thing
  being predicted — is never revealed. Pass `use_target_context=False` for the
  stricter setting.
- **Hybrid weights are tuned on validation, never on test.**

## Architecture

```
travelnext/
├── data/                     # ingested data (gitignored, regenerable)
├── notebooks/                # exploration only
├── src/
│   ├── data/
│   │   ├── sources/          # one module per free API
│   │   ├── build_destinations.py    # ingestion pipeline
│   │   ├── build_dataset.py         # features + synthetic interactions
│   │   ├── dataset.py               # loading, splitting, leakage checks
│   │   └── synthetic_interactions.py
│   ├── preprocessing/        # POI counts -> attribute features
│   ├── models/               # popularity, content, CF, hybrid, next-dest,
│   │                         # context, cold start, weight tuning
│   ├── candidate_generation/ # stage 1
│   ├── ranking/              # stage 2: features + LightGBM LambdaRank
│   ├── evaluation/           # metrics + experiment runner
│   ├── explainability/       # evidence-backed reasons
│   ├── analysis/             # EDA, bias/diversity, results rendering
│   └── service.py            # shared by the API and the UI
├── api/                      # FastAPI
├── app/                      # Streamlit
├── tests/
└── configs/config.yaml       # every knob lives here
```

`src/service.py` is deliberately shared: the API and the UI cannot drift apart
in what they recommend or how they explain it.

### Models

| Model | Idea | Handles cold start? |
|---|---|---|
| **Popularity** | Rank by observed training frequency. The bar everything else must clear. | Yes (it is the fallback) |
| **Content-based** | TF-IDF over Wikipedia text + OSM attribute profile; cosine against a recency-weighted user profile. | Yes — new destinations too |
| **Item-item CF** | Shrunk cosine over co-visitation, top-K neighbours. | No — returns zeros, by design |
| **Matrix factorisation** | Truncated SVD of the interaction matrix. | No |
| **Hybrid** | `α·content + β·collaborative + γ·popularity + δ·context`, weights searched on validation. | Yes — degrades to content + popularity |
| **Next-destination** | Adds a **transition matrix** of consecutive trips: "where did travellers go *immediately after* here", which is a sharper signal than co-visitation. | Falls back to popularity |
| **Learning-to-Rank** | LightGBM LambdaRank over the candidate shortlist. | Yes — via candidate generation |

### Context awareness

Month, trip duration, budget and origin change the ranking through real
measurements: Open-Meteo climate normals give a per-month comfort index, the
World Bank cost proxy gives a budget fit, and trip duration widens the
geographic kernel — a 2-day break favours neighbours, a 3-week trip barely
penalises distance. No live prices or flight data are used, so the system stays
free and works offline.

### Cold start

- **New user** → onboarding path: stated interests, month, budget, popularity.
- **New destination** → content features exist from ingestion, so it is
  rankable immediately; this is why the hybrid keeps a content component.
- **Unknown identifiers** → skipped and reported in `unknown_destinations`,
  never raised. The system does not crash on a stale bookmark.

## Running it

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
```

Build the dataset (needs internet once; every response is cached, so re-runs
are free and offline):

```bash
python -m src.data.build_destinations   # GeoNames -> Wikipedia -> OSM -> climate -> cost
python -m src.data.build_dataset        # features + synthetic interactions
```

Then:

```bash
python -m src.analysis.eda               # figures + reports/eda_summary.md
python -m src.evaluation.run_experiments # the full model comparison
python -m src.analysis.report_results    # reports/RESULTS.md
uvicorn api.main:app --reload            # http://localhost:8000/docs
streamlit run app/streamlit_app.py       # http://localhost:8501
pytest tests/ -q
```

### Docker

```bash
docker compose run --rm ingest       # build the dataset (once)
docker compose run --rm experiments  # train and evaluate
docker compose up api ui             # API on :8000, UI on :8501
```

PostgreSQL is available behind `--profile database` but is **not** part of the
default stack: the dataset is a few megabytes of parquet read once at startup,
so a database would add an operational dependency without buying anything.

### API

| Endpoint | Purpose |
|---|---|
| `GET /health` | Status, dataset size, data attribution |
| `GET /destinations` | Catalog listing with search, filters, pagination |
| `GET /destination/{id}` | Full record incl. climate curve and similar destinations |

## Limitations

These are real and are not worked around anywhere in the code:

1. **Interactions are synthetic.** Every collaborative and ranking result
   describes recovered generator structure, not human behaviour. This is the
   single biggest caveat.
2. **Popularity is a proxy.** Wikipedia pageviews measure online interest, not
   visitor arrivals — a city with a large diaspora or recent news coverage
   ranks higher than tourism alone justifies. Automated traffic also
   contaminates some articles: two unrelated cities were observed with
   near-identical million-view spikes, which is why the **median** monthly
   views is used rather than the mean, with `pageviews_anomaly_ratio` recorded
   as a diagnostic.
3. **Cost is country-level.** Munich and Leipzig share a band. No free,
   permissively licensed per-city cost-of-living dataset exists.
4. **OSM coverage is uneven.** Western Europe is mapped far more densely than
   much of Africa and Asia, so absolute `score_*` values favour well-mapped
   regions. The `profile_*` shares are computed within a city and are much less
   affected, which is why the content model uses those.
5. **Catalog size is bounded by politeness, not capability.** Overpass grants
   about two query slots per client, so the catalog is capped and the ingestion
   deliberately runs slowly. `ingest.catalog_size` raises it if you are willing
   to wait.
6. **The season comfort index is a heuristic** over real measurements, not a
   measurement itself. The raw `temp_m*` and `precip_m*` columns are retained
   so any consumer can define "good weather" differently.
7. **English Wikipedia only**, which biases both text features and the
   popularity proxy toward the anglophone world.

## Possible improvements

- Swap synthetic interactions for a real, licensed trip dataset — every model
  and metric would carry over unchanged.
- Session-based sequence models (GRU4Rec, SASRec) for the next-destination task.
- Per-city cost data if a permissively licensed source appears.
- Calibrate the popularity proxy against published tourism statistics for the
  countries that publish them as open data.
- Multilingual Wikipedia text and pageviews to reduce anglophone bias.
